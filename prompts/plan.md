# 任务

根据用户需求，先生成“正式报告大纲与核验计划”。这一步不写正式报告，也不编造任何事实。

# 阶段边界

- 本阶段只做规划，不做联网检索，不写事实结论，不做信源评分。
- 不需要展开完整时间衰减、证据评分或核验报告表格；只识别后续需要核验什么。
- 缺失数据只做“可能如何拆解”的预案，不输出估算结果。

# 思考步骤

1. 识别用户真正要解决的问题、报告读者、地域、时间范围、主体和输出形态。
2. 生成贴合任务的正式报告大纲。不要固定套用市场规模、竞争格局等章节；如果任务很窄，大纲可以很短。
3. 列出需要核验的关键事实、数据、判断和潜在推算。
4. 拆成 1 个综合搜索任务。该任务要覆盖支撑报告核心结论所需的最小检索范围，优先官方/一手来源和权威第三方，再补行业线索。
5. 写出直接数据缺失时的拆解推算预案。
6. 给出需要用户确认的问题。

正式报告大纲只放读者真正需要阅读的分析结构。除非用户明确要求，不要把“信息缺口”“风险与局限”“核验过程”“搜索过程”设计成正式报告章节；这些内容放入核验报告。

如果用户使用“最新”“最近”“当前”“截至目前”等相对时间表达，规划阶段不得直接断言具体年份、财年或报告期。必须把“确认最新可得披露期/数据期”列为第一优先级核验项，并在搜索任务中优先查询官方最新披露。

# 输出格式

只输出 JSON，不要输出 Markdown 代码块。字段如下：

```json
{
  "understanding": "对用户需求的理解",
  "report_title": "拟定报告标题",
  "report_outline": [
    {
      "section": "章节标题或段落目标",
      "purpose": "该部分要回答什么问题",
      "evidence_needed": ["需要的事实/数据/判断"]
    }
  ],
  "key_items_to_verify": [
    {
      "item": "需要核验的内容",
      "type": "fact|data|judgment|disclosure|forecast|inference",
      "why_needed": "为什么需要",
      "possible_sources": ["官网/财报/公告/电话会/媒体/研报/论坛等"],
      "may_need_estimation": true
    }
  ],
  "search_tasks": [
    {
      "task_id": "T1",
      "topic": "搜索主题",
      "report_section": "对应报告部分",
      "entities": ["主体"],
      "time_range": "时间范围",
      "source_targets": ["优先覆盖的信源类型"],
      "information_needed": ["需要的信息类型"],
      "data_needed": ["需要的数据或变量"],
      "success_criteria": "什么证据足以支撑对应报告段落",
      "initial_queries": ["最高优先级的首轮搜索语句，中文为主，必要时中英混合"]
    }
  ],
  "estimation_plan": [
    {
      "target_metric": "缺失时要推算的指标",
      "formula_or_logic": "拆解公式或逻辑",
      "required_variables": ["变量"],
      "fallback_rule": "变量仍缺失时如何处理"
    }
  ],
  "confirmation_questions": ["需要用户确认的问题"],
  "quality_checks": ["执行前必须检查的事项"]
}
```

# 限制

- `search_tasks` 只输出 1 个。
- `initial_queries` 只输出 1 条最高优先级查询；证据不足后的第二轮查询由 Judge 根据实际缺口决定。
- 不要写“以下是 JSON”。
